# Fab loss profiles and compatible-run attribution

Status: V8 project-aware measured loss ranking conserves completed tracked-lot queue time at exact process-input and transport-dispatch locations, retains exact event-backed Q-time step contributors, attributes productive-equipment input starvation to explicit Resource/Buffer/immediate-supply-state intervals inside observed inter-job opportunity windows, partitions local transport blocking by immediate physical cause, decomposes maintenance and qualification into exact Device/service-path contributors, traces verified yield outcomes back to observed applied defect-origin events, reports mode-level authored/prevented/applied quality evidence, includes value-weighted delivery mismatch, and is projected from both hash-compatible runs and loss-guided Design iterations.

Related: [[docs/design/industrial-boundaries]], [[docs/design/lot-tracking]], [[docs/design/product-routes]], [[docs/design/operator-workbench]], [[docs/design/design-programs]], [[docs/CLI]], [[plans/memory-fab-design-loop]], [[plans/loss-guided-design]].

## Purpose and authority

Nominal production analysis answers whether configured jobs and material contracts can balance. It does not explain why a re-entrant fab lost realized service during one operating window. Once a completed run exactly matches the current engine, selection-scoped execution identity, and selection, the workbench may derive a second evidence layer from its recorded `FactoryMetrics` and `FactoryEvent` stream.

`analyzeFabLossProfile()` is a deterministic source-neutral projection of existing evaluator-owned measurements and events plus the compiled project's Device capabilities. It does not simulate again, change an evaluator score, or claim calibrated semiconductor economics. Every normalization, including active-device utilization weighting, is returned as scalar evidence. `analyzeFabLosses()` adds one hash-compatible persisted-run identity to that profile for Workbench use; the ranking model itself owns no run provenance.

## Compatibility gate

A run is current only when World, Blueprint, Scenario, and Objective ids plus the engine and exact selection-scoped execution identity match the compiled project. Selection equality or engine equality alone is insufficient; unselected catalog inventory is irrelevant. An older incompatible run remains historical evidence but cannot drive current loss attribution or outrank current nominal diagnostics.

## Named buckets

For a run with a tracked lot family, Core ranks non-zero measured signals in these stable buckets:

- delivery portfolio: mean unmet share across evaluator-owned contracts, with exact demanded, delivered, shortfall, above-demand output, gross value, shortage penalty, and net value evidence;
- release and admission: pending scheduled lots plus CONWIP/control and physical-capacity release blocks;
- tracked-lot queue congestion: mean lot queue time as a share of mean cycle time, with process/move time and the measured productive bottleneck context retained separately;
- productive-equipment input starvation: explicit runtime material-shortage intervals intersected with a productive Device's completed-job-to-next-start opportunities after excluding overlapping maintenance/qualification, changeover, failure, output blocking, batch/campaign hold, tooling/facility wait, sleep/wake, and power intervals. Every interval preserves all simultaneous missing Resource/Buffer inputs and each immediate local supply path/state. The opportunity denominator spans first observed start through last observed finish, while warm-up before the first start, drain after the last finish, single-job Devices, and exception-only rework equipment remain auditable boundary evidence rather than ranked starvation. Any eligible opportunity gap without an explicit shortage remains `unattributedGapTicks` rather than being guessed as material loss;
- batch formation: formation holds, timeout releases, and per-lot batch wait;
- setup and campaign control: completed powered changeover work and campaign holds are conserved across stable transition contributors. `null → group` commissioning is separate from recurring `group → group` production changeover, and voluntary campaign holds remain a third mechanism. A completed transition binds its Device, directed setup groups, target Process, Process input/output Resources, available lot and unique Route/step context, start/finish boundary, transition power, and energy. Target Process authority comes from the ordered immutable `changeover-finish → device.start` event sequence; a setup group with exactly one compiled Process is the only fallback. Open and released holds preserve their exact duration and release cause;
- maintenance and qualification: service, qualification, consumable wait, and crew wait are conserved across ordered Device contributors. Each contributor retains cause/trigger counts, phase completions and cancellations, drift exposure, exact service and qualification consumable quantities, the production Process set, the serviced Device, and every provider Device observed in service/qualification events. Compiled eligible providers are used only when no assignment event exists, so a blocked path remains inspectable without pretending an assignment occurred;
- reusable tooling contention and fab facility contention: their independent provider waits, blocks, cancellations, and interruptions;
- equipment failure and power interruption: measured Device status time;
- local transport blocking by cause: only measured blocked item-time is ranked. Every blocked transit carries one immediate physical cause and stage: line-cell contention, endpoint service capacity, endpoint power interruption, or endpoint failure at the line, loader, or unloader. Tracked-lot mean transport time remains explicit cycle-time and bucket context, but ordinary required movement contributes no loss score by itself;
- Route Q-time: violated lots and step visits, with ordered event-backed contributors grouped by Route step and waiting mechanism. Every contributor retains Process ids, Route and physical Device subjects, unique lot and visit counts, total/mean/maximum queue time, the evaluator-owned limit, and total/maximum overrun. A multi-lot Process with no overlapping service work is classified as `batch-companion-wait`; service or qualification events overlapping the violating lot's queue interval are classified as `maintenance-qualification` and retain their provider Device; the honest fallback is `equipment-availability`;
- verified yield and quality loss: first-pass results over actually inspected unique lots, plus rework, scrap, escapes, and lost lot-derived output; unfinished WIP is not called a quality failure. Ordered contributors group authored quality excursions, equipment process drift, and defect-bearing Route Q-time violations by exact source Process, Device, and Route step, then follow each source lot/defect pair through detection, rework attempt, repair, persistence, quality scrap, or output-profile escape. Equipment-drift aggregates remain available as independent cross-check evidence.

Each bucket retains exact scalar evidence, a contributor array, and the strongest available Device, connection, Route, or project subject. Most buckets expose an empty contributor array rather than inventing detail. Q-time emits Route-step contributors. Input starvation emits ordered `material-input-shortage` Device contributors with Process ids, job counts, opportunity span, excluded unavailability, exact attributed and unattributed time, and an `inputStates` partition. Every state names its conserved duration plus simultaneous Resource, Buffer, treatment, quantity, connection, source Device/Buffer/status/inventory, in-flight, and sorter-endpoint observations. Contributor shortage-state ticks must sum exactly to `starvationTicks`; immediate Device and connection subjects are projected without recursive graph-root claims. Maintenance contributors sort by total Device time, service time, then stable Device id; their service, qualification, input-wait, and crew-wait components must independently sum to the evaluator totals or attribution rejects the metrics. Their `consumables` object keeps per-Resource service and qualification quantities separate rather than flattening physical kits into prose. Power interruption emits one contributor per positive `unpoweredTime` Device, including its exact grid, optional loader/unloader connection and stage, shortage/restoration counts, Device peak deficit, and the grid's generated/demanded/served/unserved energy, peak deficit, and storage envelope. Contributor ticks must conserve the evaluator total; the affected Device, connection, and grid distributor remain typed Factory subjects. Transport blocking emits only positive connection contributors with exact Resource mix, departed/delivered flow, capacity, utilization, average in-flight inventory, total blocked item-ticks, blocked fraction, the complete four-cause partition, and endpoint-stage capacity/power/failure shares. The contributor mechanism is its largest immediate cause, while all shares remain visible; a queue propagated into an occupied upstream cell remains line contention at that transit rather than being rewritten as an unproven graph-level root cause. The four cause totals must sum exactly to total blocked item-time or attribution rejects the metrics. Contributors sort by blocked time, blocked fraction, then stable connection id. Yield emits defect-origin contributors with exact defect classes and lot ids plus introduced, detected, reworked, repaired, persistent, scrapped, and escaped counts. Yield contributors sort by observed scrap, escape, persistence, rework, introduced lots, then stable id; because a set-valued latent defect may receive multiple observed introductions, contributors are investigative chains rather than an additive decomposition. Input contributors sort by `starvationTicks × utilization`, then starvation and stable id; utilization selects an investigation subject but does not change the bucket denominator. Queue congestion still prefers the evaluator's productive bottleneck. Zero-signal buckets are omitted. Results are deterministically sorted by descending score and stable id; Q-time contributors sort by visit count, total overrun, then stable id. `primary` is the first bucket and `chain` contains every non-zero bucket in that order, so an exhausted bounded decision advances to the next realized signal without falling through an arbitrary display limit. Delivery overflow is reported as context but is not itself a loss because above-demand product remains valuable under [[docs/design/delivery-contracts]].

## Interpretation boundary

Bucket scores normalize heterogeneous measured delays and counts so an operator or Agent can prioritize investigation. Several signals overlap—for example, a batch hold contributes to queue time, and a power interruption can extend Route Q-time. Scores are therefore not additive units of foregone output, a Shapley decomposition, or proof that changing the top bucket will recover a stated quantity.

The contract always carries this caveat. Product language uses “ranked signal” and “loss chain,” not fabricated percentage causality. A future counterfactual attribution model must be a separate evaluator contract with controlled reruns.

## Design iteration projection

A Design Program evaluates the exact driver case against its current best Blueprint before every proposal. On a fresh run, the locked Benchmark case used for scoring retains an ephemeral complete trace long enough for Core to hash its metrics and derive the source-neutral `FabLossProfile`; scoring and causal attribution are two projections of one deterministic execution. A historical continuation node without a retained invocation-local trace is explicitly replayed and must reproduce its recorded evidence before proposal generation. The immutable iteration records only `driverEvidence`; it never persists the trace, invents a run id, or calls invocation-local evidence “compatible.”

Project proposal-provider API V8 receives a deeply frozen copy of the V8 loss profile, Objective evidence, explicit selected-branch identity, proposal-time leader comparison, and lineage-local history. A loss-focused provider therefore sees exact tracked-lot queue ownership, input Resource/Buffer/supply state, and transport mechanism before it names an intervention. A promotion-ready loss-focused leader must return `addressedLoss`; an Objective-focused leader returns an exact `addressedObjectiveTarget`; a blocked alternative may instead return `addressedCase`. Missing, fabricated, and mutually conflicting targets are rejected before candidate compilation. Historical targets describe attempts made from this Blueprint lineage; they do not alter the current chain or promotion boundary. Every target is a falsifiable rationale, not proof that its patch will succeed: exact replay, the complete locked Benchmark, and frontier policy still supply authority.

The memory-fab provider annotates ordinary candidates with loss buckets and repair candidates with locked case ids. It chooses a case repair first when the selected alternative is blocked; otherwise it ranks the least-attempted eligible loss before chain position and authored order. It never repeats a strategy, skips a patch whose exact policy is already installed, and stops when it has no matching intervention. One repair adds ordinary powered N+1 fab-utility capacity for `facility-interruption`; a later repair adds spatially independent N+2 capacity only after a dedicated layer-two lithography bay exists. Another recognizes only the exact existing `3 / 12000` lithography campaign and removes voluntary hold for `lithography-interruption`.
